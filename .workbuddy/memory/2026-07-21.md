## 内存/CPU 问题排查（SSE + SQLite + WebGPU）

### SSE 轮询导致 SQLite prepared statement 泄漏（已确认）
- `apps/editor/app/api/scenes/[id]/events/route.ts` `POLL_MS=250`（每秒 4 次轮询 `listSceneEvents`）。
- `packages/mcp/src/storage/sqlite-driver.ts:97` 每次 `query()` 都 `db.prepare()`，无缓存、无 finalize/close。
- `packages/mcp/src/storage/sqlite-scene-store.ts` 的 `listSceneEvents`/`getRow` 等都走这条无缓存路径。
- 第二条 SSE：`apps/editor/app/api/ai-harness/runs/[id]/events/route.ts` `POLL_MS=500`。
- store 本身是单例（`apps/editor/lib/scene-store-server.ts`），DB 连接复用，但 statement 不复用。
- 每条 scene_event 带整份 `graph_json`，且 `rowToSceneEvent` 每次 `JSON.parse` 全量图 —— CPU/内存放大主因。
- `scene_events` 表无清理策略，只增不减。

### WebGPU device lost: "A valid external Instance reference no longer exists"
- 监听器：`packages/viewer/src/components/viewer/index.tsx` `GPUDeviceWatcher`（行 94-147），监听 `device.lost` + `uncapturederror`。
- renderer 创建：同文件 `THREE.WebGPURenderer` + `WEBGPU_RENDERER_CACHE`（WeakMap by canvas），缓存 in-flight Promise。
- 这条 Dawn 报错是 **GPUInstance（浏览器 GPU 进程里的实例）失效**，不是显存耗尽；典型诱因：GPU 进程崩溃/重启、多次 adapter/device 申请未释放累积到上限、或标签页被浏览器回收 GPU。
- 与上面内存问题的关联：Node 进程 4.6GB 私有内存 + 持续 CPU 主要是**服务端**问题；WebGPU 崩溃是**浏览器端**，两者独立，但服务端 SSE 的 `graph_json` 反复推送会让客户端反复 `applySceneGraphToEditor` → 几何重建 → GPU 资源压力增大。
- 恢复路径：目前只有提示重新加载页面（`setRendererHealth('lost')`），`isGpuOutOfMemoryError` 只匹配 OOM，不匹配 instance-lost 这类错误。

## 已实施的修复

### #1 SQLite statement 缓存（packages/mcp/src/storage/sqlite-driver.ts）
- `adaptNodeDatabase` / `adaptBunDatabase` 增加按 SQL 字符串缓存 prepared statement 的 Map，close 时清缓存 + close db。
- 关键坑：`node:sqlite` 的 StatementSync 方法必须带 receiver 调用（detached 会 "Illegal invocation"），且没有 `finalize()`；缓存的是绑定后的包装对象。
- 验证：mcp storage 测试 17+39 全过；biome clean；tsc 唯一报错是预先存在的 `construction-tools.ts` 引用 `getActiveRoofHeight`（与本次无关，已用 stash 验证）。

### #3 WebGPU renderer 卸载销毁（packages/viewer/src/components/viewer/index.tsx）
- 新增 `installDeviceDestroyOnDispose`：patch `renderer.dispose()`，追加 `device.destroy()` 并从 `WEBGPU_RENDERER_CACHE` 删除 entry。three 的 WebGPURenderer.dispose() 原本不 destroy GPUDevice，R3F unmount 调 dispose 时就走这条路。
- `GPUDeviceWatcher` 的 `device.lost` 回调增加 `reason === 'destroyed'` 早退，避免主动销毁被误报为 device lost。
- 验证：viewer tsc --build 通过；biome clean。
